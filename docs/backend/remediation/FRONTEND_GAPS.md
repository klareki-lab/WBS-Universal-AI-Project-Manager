# Astra backend-gap review

Reviewed `apps/frontend/docs/BACKEND_GAPS.md` at Astra branch commit **091e37d6df5214c1ec91ccc50edb45d3002f563c** (`origin/feat/frontend`). No frontend source or branch was changed. These classifications describe the backend contract; they do not claim the frontend has been updated or end-to-end tested.

| # | Classification | Decision / integration requirement |
|---|---|---|
| 1 Native task without a plan | Confirmed product gap; explicitly deferred direct-write feature | This architecture materializes task creation through immutable plans and human approval. For a manual task, submit a one-task draft, review, approve and publish. Direct POST tasks is absent (404), not a browser-local substitute. Keep direct-create controls disabled or route them through planning. Allowing direct task creation would need an explicit product decision about approval exemptions, not an audit hotfix. |
| 2 Edit existing plan drafts | Existing capability with explicit revision/rebase policy | GET saved snapshot, edit a client copy, POST createPlan/proposeChanges with the complete validated candidate and current base_project_version. Every edit creates a new immutable numbered version; no in-place edits. On 409 refresh state and explicitly reconcile/review a new candidate. Never automatically relabel an old AI operation's result to the latest base; enqueue a new operation instead. |
| 3 Plan diff and approval history | Existing trusted snapshots for client diff; confirmed history gap fixed | Compute a display-only diff between exact backend GET snapshots/hashes. No backend comparison endpoint is needed to authorize approval. GET plan approvals now returns immutable decisions, reviewer UUIDs and revocations. POST revoke-approval implements the declared pending-approval policy. Reviewer display-name enrichment and server-computed diff remain deferred presentation enhancements. |
| 4 Category/target date/budget/constraints | Confirmed product gap; explicitly deferred schema feature | v1.1.0 retains name/description/status/version and rejects unknown properties. Do not fabricate these fields or treat browser storage as canonical. Product must define budget units/currency, confirmed-vs-proposed dates and constraint semantics before a separate contract/migration. No original backend requirement defines those fields. |
| 5 Session/CSRF after reload | Confirmed product gap fixed | Human GET /api/v1/auth/csrf bootstraps a stable session-bound CSRF token after reload. Login still supplies it; the session remains HttpOnly and SameSite=Strict. Bootstrap does not rotate new-session tokens between tabs. The first bootstrap of a legacy v1.0 session replaces its old random CSRF value once; old tabs must bootstrap again. |
| 6 Chat/Q&A/history/proposal listing | Existing planning/correlation; broader chat features explicitly deferred | Planning returns durable operations and saves structured drafts. Conversation references, plan versions, audit and operation history exist. Read-only conversational Q&A, arbitrary message history and a generic proposal inbox are outside the agreed backend/MCP boundary. Disable unsupported live-mode controls until a separate lifecycle/contract is agreed; no direct model calls were added to the domain. |
| 7 Safe mutation recovery | Existing capability; choose durable client keys | Persist each exact pending command's user/project/method/path/payload/Idempotency-Key **before sending**. After reload authenticate, bootstrap CSRF and retry that exact command/key; the backend either replays the committed result or executes it once. Do not automatically replay a different user's pending commands or change payload under a saved key. Current permissions are rechecked, including creation replay. A lookup-by-key endpoint is not necessary for this recovery protocol and is deferred. |
| 8 Frontend build lockfile | Frontend-owner action | Astra must generate/commit its own lockfile and run its build gates. No backend fix is appropriate; this workstream did not edit frontend dependencies. |

## Hostname coordination

Backend defaults now advertise **http://localhost:13081** with frontend **http://localhost:5173** and ALLOWED_ORIGIN=http://localhost:5173. Bind addresses/ports remain loopback-only. Chromium verifies login, session read, reload bootstrap, mutation, independent cookie storage and cross-project rejection for this arrangement. Different localhost/127.0.0.1 hostnames intentionally remain incompatible with Strict cookies.

Astra's LIVE_INTEGRATION.md currently describes an alternative consistent 127.0.0.1 arrangement on frontend port 15173, API port 13081 and matching ALLOWED_ORIGIN. That arrangement is valid only when the browser actually uses 127.0.0.1 for both. Astra should either adopt the canonical localhost defaults or keep that fully matched alternative, update its bootstrap calls and verify its actual UI. CORS alone does not make different sites share Strict cookies.
